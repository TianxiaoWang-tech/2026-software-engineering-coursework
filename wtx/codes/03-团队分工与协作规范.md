# 团队分工与协作规范

**项目：** 基于 OpenHarmony 操作系统的家居设备控制系统（第十五届中国软件杯 A9）
**文档编号：** PM-HOME-OH-001
**版本：** V1.0
**编写日期：** 2026-11-01

---

## 1. 分工原则

| 原则 | 说明 | 反面案例 |
|---|---|---|
| **竖切而非横切** | 每人负责一条端到端可运行的业务线，而不是"一人写所有 UI、一人写所有逻辑" | 横切会导致全员互相等待联调 |
| **契约先行** | 第 1 周结束前冻结接口与数据结构，之后只允许"新增"不允许"修改" | 边写边改接口 → 三份代码无法合并 |
| **目录单一所有权** | 任一文件在同一时间只有一个负责人，禁止跨目录修改 | A 顺手改了 C 的通信层 → 冲突无法自动合并 |
| **产出可聚合** | 每人交付"目录 + 章节 + 证据"，格式统一，AI 可拼接 | 交付一份自由格式的 Word → 无法合并 |
| **需求编号贯穿** | 代码、测试、文档全部标注 `FR-x.y`，聚合时可自动生成追溯矩阵 | 无法证明"需求都实现了" |

一人一列，只写自己的列；跨列需求走契约，不直接改代码。

```

│   ├── gateway-api.d.ts       #   双端通信协议（请求/响应/推送）

│   ├── domains/access/        # 【D】门禁中心

│   └── demo/                  # 【D】演示模式与仿真脚本
│
├── mobile/                    # 【C 独占】HarmonyOS App 独立工程
│   ├── entry/src/main/ets/pages/
│   ├── entry/src/main/ets/view/

├── prompts/                   # 全员分人提交 AI 提示词记录（见 04 号文档）
```

**规则：** 目录名后的方括号即所有权。AI 聚合时按此矩阵拼接，天然无冲突。

## 4. 契约冻结（第 1 周必须完成）

四份 `.d.ts` 是全项目的"宪法"，冻结后只增不改。

| 契约文件 | 内容 | 冻结时间 | 变更流程 |
|---|---|---|---|
| `model.d.ts` | Area / Device / Entity / Capability / Sensor / DoorLock | 第 1 周末 | A 发起，全员确认，记录变更日志 |
| `driver.d.ts` | `Driver` SPI：discover / attach / set / detach / onState | 第 1 周末 | 同上 |
| `ac-adapter.d.ts` | `AcAdapter`：brand / transport / capabilities / set / parseState | 第 1 周末 | 同上 |
| `gateway-api.d.ts` | 双端所有消息：类型、字段、错误码 | 第 1 周末 | 同上 |

**为什么必须先冻结：** 四个人并行开发时，唯一能让"AI 最后直接合并"的前提是——大家写的是同一套类型。契约一变，四份代码同时失效，AI 只能重写而不是合并。

## 6. 文档聚合规则（AI 可直接拼接）

### 6.1 章节归属

每人只写自己负责的 `###` 二级小节，标题格式固定：

```markdown
### 3.2 照明中心实现        <!-- owner: B -->
```

AI 聚合时按 `owner` 注释与标题序号排序，**不需要人工重排**。

### 6.2 写作模板（每人必须遵守）

```markdown
### <章节号> <标题>          <!-- owner: <A|B|C|D> -->
> 对应需求：FR-x.y, FR-x.z

**设计说明**
（200 字内，讲清"为什么这样做"）

**关键实现**
（代码片段或流程说明，≤ 30 行）

**验证证据**
- 测试用例：AT-xx
- 截图/日志：<相对路径>
```

### 6.3 禁止事项

- 禁止修改他人章节（要改就在评审会上提，由 owner 改）
- 禁止自创章节编号（编号由本文档第 3 节目录矩阵分配）
- 禁止粘贴大段无来源结论（每条结论须有代码/截图/数据支撑）

## 7. Git 与周节奏

| 项 | 约定 |
|---|---|
| 分支 | `main`（可交付）、`develop`（集成）、`feat/a-core`、`feat/b-climate`、`feat/c-mobile`、`feat/d-access` |
| 提交信息 | `[FR-2.4] 实现人体感应自动亮灯` —— 必须带需求编号 |
| 合并 | 每周日晚由 **A** 把四条 feat 分支 squash 合并到 `develop`，冲突由 A 裁决 |
| 标签 | 每周打 `w1`…`w15` 标签，便于回溯"哪一周坏了" |
| 禁止 | 直接推 `main`；跨目录修改；一次提交超过 500 行（无法 review） |

**集成节点（硬性）**

| 周次 | 集成目标 | 判定标准 |
|---|---|---|
| W2 | 契约冻结 | 四份 `.d.ts` 评审通过，四人各写 1 个 mock 通过类型检查 |
| W4 | 冒烟链路 | 手机端 App 能控制一盏虚拟灯（C ↔ A 接通） |
| W7 | 四大中心演示 | B/D 的业务可在仿真器上跑通 |
| W10 | 安全验收 | 三层加密全部通过 AT-08 |
| W13 | 作品冻结 | 只修 bug，不加功能 |

## 8. AI 聚合机制

### 8.1 聚合不是"最后一次性合并"

分三层增量聚合，越早越好：

| 层级 | 频率 | 输入 | 输出 |
|---|---|---|---|
| L1 契约校验 | 每周 | 四份 `.d.ts` + 各人代码 | 类型不一致清单（AI 直接指出谁偏离契约） |
| L2 文档拼接 | 每两周 | 各人 `###` 章节 | 统一的总体设计/手册草稿 |
| L3 全量聚合 | 结题前 | 代码树 + 文档 + 测试数据 + 截图 | 提交包（源码、文档、PPT 大纲、视频脚本） |

### 8.2 每人提交"聚合包"（固定五件套）

```
handoff/<姓名>/
├── code/            # 只含自己目录下的代码
├── sections/        # 自己负责的 markdown 章节（带 owner 注释）
├── evidence/        # 截图、日志、录屏、测试输出
├── manifest.json    # 交付清单（见下）
└── notes.md         # 已知问题、未完成项、需要他人配合的点
```

`manifest.json` 格式（AI 靠它做拼接与校验）：

> **提示词记录同步提交：** 凡由 AI 产出的代码或文档，须在 `prompts/<姓名>/` 下同步提交一条提示词记录（格式见《AI 使用与提示词提交规范》PM-HOME-OH-002），聚合时作为一致性审计与"AI 使用声明"的输入。

```json
{
  "owner": "B",
  "requirements": ["FR-2.1", "FR-2.6", "FR-3.4", "FR-3.5"],
  "paths": ["gateway/domains/lighting", "gateway/domains/climate"],
  "docs": ["docs/03-design.md#3.2", "docs/03-design.md#3.3"],
  "status": { "FR-2.1": "done", "FR-3.5": "done", "FR-4.x": "na" },
  "depends_on": ["contracts/model.d.ts@v1", "gateway/services/ws@v1"]
}
```

### 8.3 聚合 Prompt 模板（交给 AI 时直接粘）

```text
你是本项目的集成工程师。以下是四名成员交付的聚合包，请完成三件事：

1. 一致性检查
   - 对照 contracts/*.d.ts，列出每份代码中偏离契约的类型与字段（文件:行）
   - 检查文档章节编号是否与目录矩阵冲突

2. 需求覆盖统计
   - 汇总四个 manifest.json 的 status，生成"需求 → 实现状态 → 证据"矩阵
   - 标出所有未实现（pending）或无人认领的 Must 级需求

3. 生成提交包
   - 按 docs/ 目录拼装 03-design.md（按章节号排序，保留 owner 注释）
   - 生成 05-test-report.md 的覆盖表
   - 输出缺失项清单与建议补充顺序

输入：<粘贴 contracts 摘要 + 四个 manifest.json + 目录树>
```

### 8.4 聚合验收清单（AI 输出后人工确认）

- [ ] 每个 Must 级需求有实现文件 + 验收用例 + 证据
- [ ] 两份文档中同一需求的描述一致（无矛盾指标）
- [ ] 代码可编译，HAP 可安装
- [ ] 演示视频脚本与实现功能一一对应（不能演示没做的）

## 9. 常见坑（务必避免）

| 坑 | 后果 | 规避 |
|---|---|---|
| 四人各自让 AI 从零生成整个项目 | 四套风格，无法合并 | 只生成自己目录内的代码，接口从契约继承 |
| 契约边写边改 | 全员返工 | 第 1 周冻结，变更走评审 |
| 文档各写一份 Word | 无法拼接、口径不一 | 统一 markdown 章节 + owner 注释 |
| 最后两周才联调 | 发现接口不匹配，来不及改 | 每周日集成，W4 必须跑通冒烟链路 |
| 只管功能不管证据 | 文档质量 10 分全丢 | 每完成一个 FR 立即存截图/日志 |
| 硬件进度不可控 | 演示无法进行 | D 优先做仿真器，硬件为加分项 |
