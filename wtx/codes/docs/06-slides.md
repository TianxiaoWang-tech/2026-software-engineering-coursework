## P1 封面

- 副标题：本地优先 · 三层加密 · 跨品牌兼容
- 团队：A/B/C/D 四人（姓名 + 分工）

## P2 痛点（30 秒）

- 家居 App 底座依赖 iOS/Android，国产化程度低
- 单一厂商云绑定，断网即失控
- 跨品牌空调各用各的 App，无法统一联动
- 控制数据在公网传输，隐私存疑

**配图：** 四个手机 App 图标的"碎片化"示意。
**要点：** 一句话收口——"问题不是功能不够，是底座和协议不对"。

## P3 我们的方案（40 秒）

- 双端架构：**OpenHarmony 网关（常驻）+ HarmonyOS 手机（远程）**
- 本地执行：控制/场景/定时不依赖云
- 统一能力模型：设备差异被驱动层吸收
- 三层加密：传输层 / 数据层 / 密钥层

**配图：** 架构分层图（取自设计文档 §2.1）。
**要点：** 强调"网关才是中控"，手机只是入口。

## P4 四大中心实现（60 秒）

| 中心 | 能力 | 亮点 |
|---|---|---|
| 照明 | 远程开关、调光、色温 | 人体感应 + 光照阈值，夜间低亮度 |
| 温湿度 | 实时采集、阈值联动 | 超温/超湿自动开空调，带防抖 |
| 空调 | 三品牌统一控制 | **能力子集不同 → 界面置灰**，新增品牌零改界面 |
| 门禁 | 远程开门 | 二次确认 + 留痕 + 未关告警 + 自动上锁 |

**配图：** 四张手机截图。

## P5 技术创新点（50 秒）

1. **能力模型 + 适配器**：同一界面控格力/美的/海尔，品牌差异（模式集、温度下限、摆风）全部收敛在适配器里
2. **协议自研**：MQTT 3.1.1 与 WebSocket 均为自研实现（零依赖），便于在 OpenHarmony 侧形态裁剪
3. **三层加密落地**：X25519 协商 + AES-256-GCM 信封 + KEK/DEK 密钥轮换，且密钥不出安全边界
4. **仿真即真机**：仿真驱动实现同一 SPI，无硬件可完整演示

**配图：** 三个品牌码值映射截图（`GREE:MODE:0x01` / `MIDEA:MODE:0x02` / `HAIER:MODE:0x12`）。

## P6 实测数据（40 秒）

| 指标 | 实测 |
|---|---|
| 自动化测试 | 46 项全通过 |
| 控制指令往返 | ~15 ms（本机，含模拟执行） |

**要点：** 数据要具体，别写"很快""很稳定"。

## P7 安全设计（40 秒）

- 传输层：TLS（生产必开）
- 数据层：AES-256-GCM，AAD 绑定报文序号，重放直接拒绝
- 密钥层：KEK 包裹 DEK，可轮换，文件内无明文密钥
- 权限：admin/member/guest 三级，门禁开门仅前两级

**配图：** 握手时序图 + 抓包密文截图。

## P8 可扩展性（30 秒）

```
新增一个品牌空调 = 新增一个适配器文件 + 注册一行
新增一种协议     = 实现同一个 Driver SPI
```

- 证据：三个品牌共用一套界面与场景规则，内核零改动
- 对比：Home Assistant 靠 1563 个集成，我们靠**一个契约 + N 个实现**
