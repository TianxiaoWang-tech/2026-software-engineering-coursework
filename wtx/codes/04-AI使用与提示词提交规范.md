# AI 使用与提示词提交规范

**项目：** 基于 OpenHarmony 操作系统的家居设备控制系统（第十五届中国软件杯 A9）
**文档编号：** PM-HOME-OH-002
**版本：** V1.0
**编写日期：** 2026-11-01

---

## 1. 为什么要提交提示词

| 目的 | 说明 | 不做的后果 |
|---|---|---|
| **可追溯** | 每段 AI 生成代码能追到需求、责任人、模型与轮次 | 答辩被问"这段是谁写的"答不上来 |
| **可复现** | 同一提示词 + 同一契约能复现同类产出 | 出问题只能推倒重写 |
| **可聚合** | AI 汇总时靠记录判断一致性、算 AI 占比、生成声明 | 只能人肉比对，文档质量 10 分难拿 |
| **合规** | 大赛强调"展示真实"，主动披露 AI 使用反而加分 | 被认为代做，风险高 |

> **先确认赛规：** 提交前请核对《第十五届中国软件杯大赛规程》中关于 AI 工具使用的条款；若要求声明，直接引用本文档第 10 节的声明模板。

---

## 2. 五要素：一条记录必须包含

| 要素 | 内容 | 为什么必须 |
|---|---|---|
| ① 元数据 | id / owner / 日期 / 关联需求 FR / 目标模块 / 模型 / 轮次 | 机器可检索、可统计 |
| ② 意图 | 一句话说明"要 AI 干什么" | 区分"探索"和"实现" |
| ③ 提示词原文 | **完整粘贴，不许改写润色** | 改写即失去可复现性 |
| ④ 人工修改 | 采纳了什么 / 改了什么 / 丢弃了什么 | 证明不是照抄，是工程判断 |
| ⑤ 证据 | 落地文件路径 + 验收用例编号 | 聚合时生成追溯矩阵 |

## 3. 目录与命名

```
prompts/
├── index.jsonl                  # 【A 维护】全员索引，一行一条，供 AI 直接读
├── _template.md                 # 单条记录模板
├── A/                           # 【A】内核/契约/安全
│   ├── 20261103-01-driver-spi.md
│   └── 20261105-02-huks-keygen.md
├── B/                           # 【B】照明/温湿度/空调适配
├── C/                           # 【C】移动端
├── D/                           # 【D】门禁/面板/演示
└── library/                     # 复用型提示词模板（跨人共享，A 审核入库）
```

**命名规则：** `<YYYYMMDD>-<两位序号>-<模块>-<事项>.md`
例：`20261103-01-lighting-motion-rule.md`

**id 规则：** `<负责人>-<YYYYMMDD>-<序号>`，例：`B-20261103-01`

## 4. 单条记录模板

复制 `prompts/_template.md`，逐项填写：

```markdown
---
id: B-20261103-01
owner: B
date: 2026-11-03
requirement: [FR-2.4, FR-2.5]
module: gateway/domains/lighting
model: <填写实际使用的模型名>
round: 1
status: adopted        # adopted | modified | rejected
---

## 意图
实现人体感应自动亮灯规则：光照 < 50 lux 且检测到人时开灯，夜间亮度 10%。

## 上下文（粘贴给 AI 的契约片段）
```ts
// contracts/model.d.ts（节选，勿改）
export interface MotionEvent { areaId: string; ts: number; }
export interface LuxReading { areaId: string; lux: number; }
```

## 提示词原文
> 【角色】你是 OpenHarmony 项目的业务模块开发者。
> 【约束】只允许修改 gateway/domains/lighting/ 下的文件；接口必须继承
> contracts/model.d.ts 中的 MotionEvent 与 LuxReading，不得新增全局状态；
> 规则需可注入 EventBus 以便单测。
> 【任务】实现 motionRule.ts：当 motion 触发且 lux<50 时，下发
> {capability:'brightness', value: 夜间?10:100}；无人 120s 后关闭。
> 【输出】只给完整文件内容，不要解释。

## 输出与人工修改
- **采纳**：阈值判断与 120s 延时计时逻辑
- **修改**：AI 使用了模块级可变变量 → 改为构造函数注入 EventBus / Clock
- **丢弃**：AI 自创的 YAML 配置结构（与契约不符，且本项目不用 YAML）

## 证据
- 文件：gateway/domains/lighting/motionRule.ts
- 测试：AT-02（人体经过自动亮灯 / 无人 2 分钟自动熄灭）
```

## 5. 索引文件（AI 直接读这里）

`prompts/index.jsonl`，一行一条 JSON，由各人提交后追加，A 每周日校验：

```json
{"id":"B-20261103-01","owner":"B","date":"2026-11-03","req":["FR-2.4","FR-2.5"],"module":"gateway/domains/lighting","model":"<model>","status":"modified","files":["gateway/domains/lighting/motionRule.ts"],"prompt":"B/20261103-01-lighting-motion-rule.md"}
```

字段含义：`status` 取值 `adopted`（直接采用）/`modified`（人工改过）/`rejected`（弃用，仅留档）。

## 6. 提交节奏与 Git 关联

| 环节 | 约定 |
|---|---|
| **何时写** | 每次让 AI 产出**要落进代码库**的内容时，同步写一条记录 |
| **何时提交** | 与代码在**同一个 commit** 提交（文档先于代码亦可） |
| **commit 格式** | `[FR-2.4][ai:B-20261103-01] 实现人体感应自动亮灯` |
| **周度汇总** | 每周日，A 运行校验（第 7 节），更新 `index.jsonl` 并打 `w<N>` 标签 |
| **探索性对话** | 不落代码的闲聊/调研**不必**逐条记录，但结论若写入文档，需补一条 `status: adopted` 记录 |

---

## 7. 每周校验清单（A 执行，5 分钟）

- [ ] 每条记录的 `module` 是否落在本人的所有权目录内（跨目录 = 违规）
- [ ] 记录中出现的类型/字段是否存在于 `contracts/*.d.ts`（不存在 = 有人绕过契约）
- [ ] `status: adopted` 的记录是否都有 `证据` 段落（无证据 = 不可采信）
- [ ] 本周新增 AI 代码行 vs 记录数是否匹配（大致 1 记录 ≈ 1 个功能点）
- [ ] `index.jsonl` 是否与 `prompts/` 下实际文件一致

## 8. 四条红线

| 红线 | 说明 |
|---|---|
| 🚫 **不得粘贴真实密钥** | 门锁密码、Token、HUKS 密钥、WiFi 密码一律脱敏为 `***` |
| 🚫 **不得让 AI 生成 `contracts/`** | 契约必须人工设计（AI 只能校验），否则接口失控 |
| 🚫 **不得改写提示词原文** | 可补充"事后说明"，但不能美化原文 |
| 🚫 **不得用 AI 生成他人目录的代码** | 所有权是聚合的前提，越界即无法合并 |

## 9. AI 聚合时如何使用这些记录

聚合阶段（L3）把 `index.jsonl` + 全部记录 + 契约一并喂给 AI，做四件事：

| 用途 | 输出 |
|---|---|
| **AI 使用声明** | 按模块统计 AI 参与度与人工修改比例，写入设计文档附录 |
| **一致性审计** | 找出提示词中自创、但契约中不存在的类型/字段 |
| **覆盖统计** | 生成"需求 → 记录 → 文件 → 用例"四列追溯表 |
| **模板沉淀** | 把高频高质量提示词提升到 `library/`，供决赛复用 |

**聚合 Prompt（直接粘）：**

```text
你是本项目的 AI 使用审计员。输入为 prompts/index.jsonl 与 prompts/ 下的全部记录。
请输出：
1) 按 A/B/C/D 统计：记录数、adopted/modified/rejected 比例、覆盖的 FR 数；
2) 列出所有 status=adopted 但缺少"证据"段落的记录（可能未经测试）；
3) 列出提示词中出现、但 contracts/*.d.ts 中不存在的类型或字段；
4) 生成"AI 使用声明"草稿（200 字），说明使用了哪些 AI 能力、人工把关方式。
```

## 11. 各角色提示词写法示例（要点）

| 角色 | 提示词必须包含的三件事 | 示例开头 |
|---|---|---|
| **A** 内核/驱动 | 契约片段 + 目标目录 + "不得新增全局状态" | 「在 `contracts/driver.d.ts` 已冻结前提下，只为 `gateway/drivers/mqtt/` 实现 `attach/set`，继承 `Driver` 接口…」 |
| **B** 业务 | 能力集定义 + 可注入依赖 + 品牌差异边界 | 「实现海尔适配器，将 `hvac_mode` 映射为品牌码值，能力子集引用 `AcProfile.capabilities`…」 |
| **C** 移动端 | 使用的 API 契约 + 性能约束（节流/局部刷新） | 「用 ArkUI 实现照明详情页，数据取自 `GatewayApi.getLightingState`，滑条节流 10 次/秒…」 |
| **D** 门禁/交付 | 安全要求（二次确认）+ 落库表结构 | 「实现远程开门，需二次确认 + 写 `AccessLog`，失败重试 1 次并推送告警…」 |

> **通用技巧：** 每次提示词都粘上相关 `contracts` 片段。这是让四人（和四个 AI）产出可合并的**唯一有效手段**——AI 看不到契约就会自己发明字段。
